# ZTAB Unified Cold-Start Test Harness

This directory contains the Zero-Trust Agent Bootstrap (ZTAB) end-to-end test
harness. The harness simulates an external developer setting up the ZTAB MCP
server on an agent, configuring it to target a Trusted Execution Environment
(TEE) server, and executing a multi-agent calendar scheduling session lifecycle.

The harness validates:
1.  **Phase 1 (Installation)**: The agent's ability to read instructions from
    `SKILL.md`, build/setup a local Python virtualenv, register the ZTAB MCP
    server in `mcp_config.json`, and configure TEE connection details in
    `backends.json`.
2.  **Phase 2 (Session Execution)**: The agent's ability to create or join a TEE
    session, accept policies, submit private inputs (calendar slots), and
    retrieve results securely using the ZTAB MCP tools.
3.  **Phase 3 (Trajectory Audit)**: Post-run verification that the agent
    successfully performed the required bootstrap steps, did not cheat (e.g. by
    using pre-existing installations), and did not perform prohibited actions
    (like sandbox escapes, executing local CLI helpers, or killing system
    processes).

---

## 1. Prerequisites

Before running the harness, make sure you have the following installed on your
host machine (workstation or GCP VM):

1.  **Docker Engine**: Required for containerized execution.
2.  **Antigravity CLI (`agy`)**: Used to perform the initial OAuth login flow to
    generate prediction credentials.
3.  **Python 3.10+**: Required for local native runs (including `pip` and `venv`
    modules).
4.  **Bazel (Bazelisk)**: Required if compiling the TEE server natively from
    source.

---

## 2. Setup & Authentication

The harness agents run a Language Server that must authenticate against the
public prediction backend to generate model outputs.

### Step 2.1: Host Directory Setup
The harness container runs as your non-root host user to prevent sandbox file
permission errors. Pre-create the run folder on your host first (otherwise
Docker will create it as `root` and lock the container out):

```bash
mkdir -p /tmp/ztab_runs
sudo chown -R $(id -u):$(id -g) ~/.gemini
```

### Step 2.2: Generate OAuth Token
Do **NOT** use `gcloud auth print-access-token`. The prediction API strictly
requires a token generated by the Antigravity OAuth client:

```bash
# 1. Install the agy CLI tool
curl -fsSL https://antigravity.google/cli/install.sh | bash

# 2. Authenticate
agy auth login
```
This caches the prediction token at `~/.gemini/` in a file matching
`*standalone-oauth-token`.

## 3. Test Execution Options

You can execute the cold-start harness in three different modes depending on
your development requirements.

### Option A: Local Host Native Execution (Fastest iteration)
Runs all components (Language Server, TEE server, and test monitor) natively
on your host machine.

1.  **Download a local GGUF model** (e.g. Gemma 2B) and save it to
    `/tmp/gemma-4-E2B_q4_0-it.gguf`.
2.  **Run the harness script**:
    ```bash
    ./test/harness/test_cold_start.sh \
      --ztab_dir $(pwd) \
      --num_agents 1 \
      --tee_mode local_build \
      --model_path /tmp/gemma-4-E2B_q4_0-it.gguf
    ```
    *This will compile the TEE server natively via Bazel, start it on port 8000,
    launch the local Language Server on a discovered port, trigger the agent,
    and run the audit.*

### Option B: Local Containerized Execution (Standard local test)
Runs the test monitor and Language Server inside a Docker container, targeting
an external local TEE server running in a separate sibling container.

1.  **Build the Harness Docker Image**:
    ```bash
    docker build -t ztab-harness:oss -f test/harness/Dockerfile .
    ```
2.  **Start the Local TEE Server Container**:
    Run a TEE server Docker image configured with model weights. Let it listen
    on port 8000.
3.  **Run the Harness Container**:
    ```bash
    docker run --rm --net=host \
      --user $(id -u):$(id -g) \
      -e HOME=/home/user \
      -v ~/.gemini:/home/user/.gemini:ro \
      -v /tmp/ztab_runs:/tmp/ztab_runs \
      ztab-harness:oss \
      --ztab_dir /ztab \
      --tee_mode connect \
      --host localhost \
      --port 8000 \
      --model MODEL_GOOGLE_GEMINI_2_5_FLASH \
      --ls_extra_flags "--cloud_code_endpoint=https://cloudcode-pa.googleapis.com"
    ```

### Option C: Remote GCP TEE VM Runbook (Production-Fidelity E2E)
Builds the server OCI image, launches an attested Confidential Space VM on GCP,
and executes the containerized harness against it.

1.  **Build and Push the Server OCI Image**:
    Pack the server binary and model weights into an OCI image and push it to
    your Google Artifact Registry (AR):
    ```bash
    gcp/build_and_push.sh \
      --ztab_dir $(pwd) \
      --image_base us-docker.pkg.dev/YOUR_PROJECT/YOUR_REPO/ztab-server \
      --gcs_bucket gs://YOUR_MODEL_WEIGHTS_BUCKET \
      --model gemma4_e4b
    ```
2.  **Provision the Attested TEE VM**:
    Use the launch script to configure the Instance Template and Managed
    Instance Group (MIG) with Intel TDX and hardware attestation:
    ```bash
    gcp/launch.sh \
      --project YOUR_PROJECT \
      --zone YOUR_ZONE \
      --image_base us-docker.pkg.dev/YOUR_PROJECT/YOUR_REPO/ztab-server \
      --ita_api_key YOUR_INTEL_TRUST_AUTHORITY_API_KEY \
      --mode setup
    ```
3.  **Launch the VM Node**:
    ```bash
    gcp/launch.sh --project YOUR_PROJECT --zone YOUR_ZONE --mode launch
    ```
4.  **Resolve the TEE VM External IP**:
    ```bash
    gcp/launch.sh --project YOUR_PROJECT --zone YOUR_ZONE --mode get-ip
    ```
    *(Let the output IP address be `<GCP_TEE_IP>`)*
5.  **Run the Containerized Harness**:
    First, build the harness image if you haven't already:
    ```bash
    docker build -t ztab-harness:oss -f test/harness/Dockerfile .
    ```

    Then run the harness container targeting the remote VM:
    ```bash
    docker run --rm --net=host \
      --user $(id -u):$(id -g) \
      -e HOME=/home/user \
      -v ~/.gemini:/home/user/.gemini:ro \
      -v /tmp/ztab_runs:/tmp/ztab_runs \
      ztab-harness:oss \
      --ztab_dir /ztab \
      --tee_mode connect \
      --host <GCP_TEE_IP> \
      --port 8000 \
      --verifier ita \
      --model MODEL_GOOGLE_GEMINI_2_5_FLASH \
      --ls_extra_flags "--cloud_code_endpoint=https://cloudcode-pa.googleapis.com"
    ```
6.  **Clean Up GCP VM Infrastructure**:
    ```bash
    gcp/launch.sh --project YOUR_PROJECT --zone YOUR_ZONE --mode delete
    ```

## 4. Script Flag Reference (`test_cold_start.sh`)

These flags control the test runner itself (passed to `test_cold_start.sh` or as
trailing arguments to the Docker run command):

| Flag | Default | Description |
|:---|:---|:---|
| `--ztab_dir PATH` | *Required* | Path to the ZTAB repository root. |
| `--num_agents N` | `1` | Number of agents to spawn (`1` or `2`). |
| `--tee_mode MODE` | `local_build` | TEE execution mode: `local_build` (local bare-metal binary), `docker_build` (local containerized TEE), `gcp_discover` (use gcloud to auto-resolve GCP VM IP), or `connect` (reuse pre-running TEE at host/port). |
| `--verifier TYPE` | `noop` | Attestation verifier to expect: `noop` (default, no attestation) or `ita` (Intel Trust Authority production attestation). |
| `--host HOST` | `127.0.0.1` | TEE server hostname/IP (used in `connect` mode). |
| `--port PORT` | `8000` | TEE server port. |
| `--model MODEL` | `MODEL_GOOGLE_GEMINI_2_5_FLASH_LITE` | Model name to instruct the agents to target. |
| `--model_path PATH` | *None* | Path to the local model file (used for `local_build` mode). |
| `--gcs_bucket URL` | *None* | GCS model bucket URL (used to pull weights in `docker_build` mode). |
| `--phase1-only` | `0` | Stop after Phase 1 (ZTAB MCP server installation and config verification) without running the session lifecycle. |
| `--dirty-state-battery` | `0` | Execute the D-series recovery tests (D1-D6) after the main test run. |
| `--reuse-dir PATH` | *None* | Reuse the sandboxes from a previous run directory (required for `--dirty-state-battery`). |
| `--app_data_dir NAME` | `antigravity-ide` | Name of the App Data directory to simulate under `HOME`. |
| `--ls_bin PATH` | `/usr/local/bin/language_server` | Path to the Language Server binary to execute. |
| `--ls_extra_flags STR` | *None* | Additional CLI flags to forward directly to the Language Server. |
| `--expected_digest SHA` | *None* | Expected TEE container image digest (for `ita` attestation verification). |
| `--gcp_project PROJ` | *None* | GCP project ID for `gcp_discover` mode VM IP resolution. |
| `--gcp_zone ZONE` | *None* | GCP zone for `gcp_discover` mode VM IP resolution. |
| `--gcp_image_base URL` | *None* | GCP Artifact Registry image base URL for `gcp_discover` mode TEE setup. |
| `--workspace_id URI` | *None* | Workspace folder URI (defaults to `file://ZTAB_DIR`). |

## 5. Troubleshooting

### 1. `Permission denied` on `/tmp/ztab_runs`
*   **Cause**: `/tmp/ztab_runs` did not exist on the host VM before launching
    the container. Docker automatically created it as `root`.
*   **Fix**: Stop the container, delete the directory
    (`sudo rm -rf /tmp/ztab_runs`), pre-create it manually
    (`mkdir -p /tmp/ztab_runs`), and run again.

### 2. `unknown model key` or startup crash
*   **Cause**: The public LS binary cannot resolve `MODEL_GOOGLE_GEMINI_2_5_FLASH`
    because it did not download the configuration registry.
*   **Fix**: Verify you passed
    `--ls_extra_flags "--cloud_code_endpoint=https://cloudcode-pa.googleapis.com"`.

### 3. Trajectory Audit Failure: `CLI fallback — agent executed cli.py`
*   **Cause**: The agent could not find the native ZTAB MCP tools, so it fell
    back to executing the raw python helper client `cli.py` (which is rejected
    by the audit). This happens when the Language Server failed to read
    `mcp_config.json` inside the sandbox due to a root permission lock.
*   **Fix**: Verify the container is launched with `--user $(id -u):$(id -g)` and
    `HOME` mapped correctly, and check that `~/.gemini` on the host VM is owned
    by your user, not root.
